Why there are two taps, not one

base_agent.py's run_async() is the only method that fires plugin_manager.run_before_agent_callback / run_after_agent_callback. resumable_orchestrator and FailFastLoopAgent call it correctly. decision_router_agent and iteration_agent call sub_agent._run_async_impl() instead — bypassing the plugin manager for their own sub-agents.

What this costs: for those two classes, Tap B still recovers full step coverage via the top-level event stream — but only after-the-fact state_delta, not the pre-execution query/template snapshot Tap A gives everyone else. The Decision Routing and Iteration specialists are told this explicitly, so a missing "before" isn't misread as evidence nothing happened. The real fix — changing those two files to call run_async() — is a code change to execution files, deliberately out of scope for this design.
Facts before judgment

Evidence Assembly — deterministic, forms no opinion

Plain code, one pass per trajectory. Per step: row count and retrieved columns from state_delta; the resolved query or URL template pre-binding (Tap A only, params never bound to literal values — keeps PII out of the harness's own tables); and a declared-vs-referenced cross-reference against every downstream step's input_keys and template expressions, producing retrieved_columns, referenced_columns, unused_columns.

Table-name extraction and reference detection are heuristic, not exact — and that's flagged to specialists as a caveat, not resolved to full precision. The heuristic only has to be good enough for a model to weigh; it never gets treated as settled fact on its own.

Aggregator

model

Cross-step root-cause reasoning, with the Tap A/B limitation caveats carried through where relevant. Confirms, revises, or rejects each candidate Recommendation before it ever reaches Fact-check.

03.5

Fact-check

different model lineage

Checks the Aggregator's own output against the underlying evidence. Deliberately a different model than the Aggregator, so it doesn't just agree with itself.

→

Human gate

not a model

The only non-model checkpoint. Approve, decline, or hold. Nothing is ever auto-applied. Declines are retained, never discarded.

04

Calibration

weekly + change-triggered

Compares harness verdicts against a human-labeled set; drift surfaces candidates for a human to act on. Never self-retrains.

Context

Zero information loss, not summarization

Every row, every column, every finding is captured and persisted in full, independent of how many model calls later reason over it. When a trajectory is too large for one call, it's split into multiple — each call's output is a complete structured list tied to exact step_ids, never lossy prose. The combine step concatenates; it never drops an entry. The one hard limit is a single step's own raw payload (e.g. one query returning 50,000 rows) — that's bounded at capture, but row count and column list are never sampled away, only the literal cell-by-cell display is.

Isolation

What a harness failure can't touch

Imports nothing from execution control-flow modules — only the two passive taps and their queues. Its own persistence tables (Trajectory, Step, CaseSummary, Verdict, Recommendation, GateDecision, CalibrationRecord), separate from agent_execution_logs / processed_data / resume_config. Its own CLI/permission surface, its own config namespace. A normal execution run is completely unaffected unless someone explicitly flags it for single-record review.
