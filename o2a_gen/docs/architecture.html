o2a_gen · design v2 · compile skills, then plan, write, review

From a review procedure to O2A workflow YAMLs

o2a_gen turns four inputs into a folder of O2A agent YAMLs: a procedure, its tools, its metadata and the agent syntax. It works the way Corpus2Skill does. First it compiles every input into browsable skill pages: Opus writes a summary card for each piece, and Nemotron embeddings group and cross-link the pieces. Then Opus agents browse those pages to plan the workflow, write each agent and review the result. The code only moves text, calls the two APIs and saves files. Every decision about the workflow comes from the models reading your inputs.

Opus 5.5 Anthropic API, claude-opus-5-5 Nemotron DeepInfra, nvidia/Nemotron-3-Embed-8B code harness only, no model

End to end

There are two phases. Compile runs once for each set of inputs and is cached by content hash, so editing one procedure section only re-cards and re-embeds that section. Generate runs Opus agents over the compiled skill store. None of the four inputs is interpreted by code. The model reads them.

Dashed blue lines show the agents reading the skill store through tools. Existing workflow YAMLs never enter either phase. They are only used by compare, after generation.

Stage by stage

Compile
1

Split into documents

code

The code cuts each input into document-sized pieces without knowing its schema, so any procedure, tools or metadata file works without code changes.

MarkdownOne document per heading, going down to the deepest level that stays under the size budget (about 1,500 tokens). Tables stay whole. Each document keeps its heading path and line range, for example procedure/attribute-instructions/testing-information/determine-if-the-loan-is-a-cramdown for lines 599–619.
YAML / JSONOne document per top-level key. A node over the budget is split into its children. List items named by name, tool_name or id use that name in the path, for example tools/tools/escrow_cya_icmp_search_documents. The raw YAML text of the node is kept.

Each document carries its family (procedure, tools, metadata or agent-syntax), a path, the raw text, a source reference and a content hash. AMBC1 plus its three companion files come to roughly 100 documents.

2

Card every document

Opus 5.5 · Batch API · effort low

Opus reads each document once and fills a card: a JSON object whose shape is set by structured outputs. The card makes a document findable, and it is where the model, not code, works out what a tool returns or which fields a procedure decision needs.

title       short name a person would search for
summary     2–4 sentences: what it is and when you would open it
names       exact identifiers it defines or uses (tools, tables, fields, keys, classes)
provides    data or capability it supplies            # tools / metadata
needs       inputs it requires
decisions   checks the reviewer makes, in order         # procedure
outcomes    results a decision can lead to (pass, fail, manual review…)
How it is calledOne Batch API request per document, keyed by custom_id = document id. The system prompt and card schema are identical in every request and cached. Batches cost 50% less, and most finish within an hour (the limit is 24 hours). --sync sends normal calls instead for quick iterations on small inputs.
CacheCards are saved in cards.json under the document's content hash. A rebuild only cards new or changed documents.
3

Embed

Nemotron-3-Embed-8B · DeepInfra

Each document is embedded as its card title, summary and names followed by its raw text. Documents are embedded as they are. Searches use the model's query format (Instruct: … Query: …), so the question "which data answers this procedure check" lands near the tools and fields that answer it.

SettingsDeepInfra's OpenAI-compatible /embeddings endpoint, 32 texts per call, first 1024 of 4096 dimensions kept, each vector scaled to unit length. The key comes from DEEPINFRA_API_KEY.
Cachevectors.npy is stored with a signature (model, dimensions, template). If the signature changes, every document is re-embedded. Otherwise only changed documents are.
4

Organise and link

codecosineOpus folder pages
Foldersprocedure/ and agent-syntax/ follow their headings, because order matters there: procedure steps run in sequence and syntax sections are one per class. tools/ and metadata/ are grouped by cosine k-means (up to 8 sub-folders, up to 12 documents per folder). An input under 12 documents stays as one folder.
Folder pagesOpus writes each folder's SKILL.md from the cards below it, bottom-up, with one batch per tree level. The page says what the folder holds and when to open it. INDEX.md lists the documents with their card titles.
Cross-linksEach procedure section gets the top 5 tools and metadata documents by query similarity, plus any whose card names appear in the section. These are written onto the page as Likely sources. Tool and metadata pages get the reverse Used by procedure links. Every document also gets its 3 nearest neighbours in the same family.
Name indexnames.json maps every exact identifier on the cards to its documents, for example escrow_cya_batch_id → the tool that produces it and the hint that gates on it. Lookups need no model call.

Links are hints for the agents. An agent confirms a link by reading the document it points to.

Generate
5

Plan the workflow

Opus 5.5 · effort high

The Planner reads the procedure tree section by section, follows each section's likely sources, and reads whatever the metadata says about pipeline shape. For escrow_cya, that includes pipeline_architecture and agent_operation_hints. The model finds these pages because they are in the store. No code looks for them. It chooses each agent's class from the agent-syntax family: deterministic classes for lookups, transforms and routing, and LlmAgent only where the syntax and procedure call for judgement.

Outputsubmit_plan takes a strict-schema tool input containing the workflow name and prefix, the pipeline inputs, and the agents. Each agent has a name, class, purpose, procedure refs, source documents, input keys, output key, and children or routes. The plan also contains the session-key table (writer and readers of each key), manual-review routes, and gaps: data a decision needs that no tool or metadata provides.
Checked by codeThe plan must match the schema, and every class name must be one the syntax cards list. A mismatch goes back to the Planner as a tool error. Nothing else is checked by code.
6

Write each agent

Opus 5.5 · effort medium · N in parallel

Each planned agent gets one Writer, and up to 8 run at a time. A Writer reads the syntax page for its class, then fetches its source documents and the procedure sections it cites. It writes the YAML with write_yaml, which parses the text and checks that the name matches the file. Any error goes back to the Writer.

Where values come fromValues are copied from tools, metadata, syntax or procedure: URLs, auth blocks, SQL, field names and ${ENV:VAR} names. Each block of fields gets a provenance comment, such as # from tools/escrow_cya_icmp_search_documents or # procedure lines 599–619.
When a value is missingThe field stays empty with # TODO: what is missing (looked in: …), and note_placeholder records it. Writers never invent a URL, table, column or connection.
7

Review and fix

Opus 5.5 · effort high · fresh context

The Reviewer never sees the Writers' reasoning, so it judges only the files. It reads the plan, every YAML, the syntax checklist (§14) and pitfalls (§15), and the procedure. It then checks six things:

  • Each procedure decision is covered.
  • Every input key is written earlier or is a pipeline input.
  • Classes and fields match the syntax.
  • Router operators match the syntax.
  • Values trace to a source document.
  • Each placeholder is really missing. The Reviewer searches for it once more.
Findingssubmit_review returns a list of findings. Each has the agent, the severity (blocking or minor), the problem, the evidence (document id or line) and the fix.
LoopEach blocking finding goes to a new Writer call for that agent, which gets its current YAML and the finding. This repeats for at most 2 rounds (configurable). Findings still open after that are listed in review.md.
8

Outputs

code
out/escrow_cya/
  agents/*.yaml          # one file per agent, name == file name
  plan.json, plan.md     # agents, classes, session keys, manual-review routes, gaps
  review.md              # findings, what was fixed, what is still open
  placeholders.md        # every empty field: agent, field, what is missing, where it looked
  run.json               # input hashes, model ids, tokens and cost per stage

o2a_gen compare --gold existing/ --gen out/escrow_cya/agents scores the output against hand-written YAMLs if you have them. It runs only after generation.

Prompt caching

Every Writer call starts with the same prefix, cached once and read by the rest. Cached input costs $0.20 per million tokens instead of $4. The first Writer runs alone until its first response has written the cache. The others then start and read it. The conversation history is cached too, so each new turn only pays full price for what it adds.

tool definitions≈2k tok
role instructions≈3k
full agent_syntax.md≈3.5k
skill root page≈1.5k
plan.json≈3k
this agent's assignment≈0.5k
tool calls and results, growinghistory cached per turn

The blue segments are cached and the white ones are sent fresh; the dark bar marks the cache breakpoint. The syntax is small enough to include whole, so every Writer sees all twelve classes and the §14 checklist without asking for them. The Planner and Reviewer share the same first four segments. Card requests have their own cached prefix, the card instructions plus the schema.

Worked example: one AMBC1 check

This traces the section Login to ICMP System through the pipeline, using the real tools and metadata files.

1 split
Lines 422–437 become one procedure document, and tools[0] (escrow_cya_icmp_search_documents) becomes one tools document.
2 card
The procedure card has the decision "is an analysis completed before the end of the computation year imaged in ICMP (Escrow Account Disclosure)". The tool card says it provides an ICMP document search for DOC_TYPE_CD 1088, needs a loan number, and needs its body built by a transformation agent.
3–4 embed, link
Query similarity and the shared name ICMP put the search tool, the icmp_outputs data-dictionary fields and the rest_api_agent syntax page on the section's Likely sources.
5 plan
The Planner reads the section, the tool and the x-pipeline-architecture stages. It plans escrow_cya_icmp_body_generator (transformation_agent), then escrow_cya_icmp_search_documents (rest_api_agent), then a not-found flag and router. The syntax section "Critical runtime requirement" and the tool description both say the payload must come from a transformation agent.
6 write
The Writer copies url: ${ENV:ICMP_SEARCH_DOCUMENTS_URL}, method: POST, the WF- headers and the bearer_dynamic auth block from the tool, adding # from tools/escrow_cya_icmp_search_documents. If a field the syntax requires isn't in the tool, the Writer leaves it empty with a TODO.
7 review
The Reviewer checks four things: the body generator's output key is this agent's input, the router uses operators from §9, the "not found" branch goes where the procedure says (additional research), and any decision that needs a field marked available: false routes to manual review (NEEDS_HUMAN).

The costs are estimates at list prices: $4 per million tokens in, $20 out, $0.20 cache reads, and half price on Batch. Thinking tokens count as output. run.json records the actual tokens and cost of each run. Batching the agent stages doesn't help, because they are multi-turn tool loops.

Opus 5.5 rules the harness follows

Model behaviourWhat the harness does
temperature is rejectedNever sends it. Runs are repeatable through cached cards and a saved plan: generate --from-plan reruns only the Writers and Reviewer.
Thinking is adaptive and always onSets effort per role: cards and folder pages low, Writers medium, Planner and Reviewer high. Sets max_tokens with room for thinking: 4k for cards, 16k for Writers, 32k for the Planner and Reviewer.
Forced tool_choice returns 400Uses auto. If an agent ends its turn without calling submit_plan or submit_review, the harness asks it to, at most twice, then stops that agent with an error.
Structured outputs are availableCards use output_config.format with the card JSON schema. Final answers use strict tool schemas.
refusal stop reasonLogs it. A refused card falls back to the raw text for embedding. A refused agent is listed in review.md for manual work. Batch requests get no server-side fallback, so they are handled the same way.
No assistant prefillNever prefills. JSON comes from the schema, not from a leading {.
The minimum cacheable prefix is 512 tokensEvery cached prefix is well over this, at about 13k tokens for agents and about 1.5k for cards.
Batch results can arrive in any orderMatches results by custom_id. Polls until the batch ends and retries failed items in the next batch.

Run it locally in VS Code

The cloud sandbox blocks api.deepinfra.com, so run it on your machine. Keys are read from environment variables only. .env is gitignored.

# terminal in VS Code, repo root
git checkout claude/sharp-pascal-p3v95o
python -m venv .venv && source .venv/bin/activate
pip install -r o2a_gen/requirements.txt

# .env (never commit)
DEEPINFRA_API_KEY=…
ANTHROPIC_API_KEY=…

# planned CLI for this design
python -m o2a_gen compile \
  --procedure inputs/AMBC1.md \
  --tools inputs/escrow_cya_toolcalls_openapi.yaml \
  --metadata inputs/escrow_cya_metadata.yaml \
  --syntax inputs/agents_syntax_updated.md \
  --out build/escrow_cya/skills
python -m o2a_gen generate \
  --skills build/escrow_cya/skills \
  --out out/escrow_cya
// .vscode/launch.json, to step through a run
{
  "version": "0.2.0",
  "configurations": [{
    "name": "o2a_gen generate",
    "type": "debugpy",
    "request": "launch",
    "module": "o2a_gen",
    "args": ["generate",
             "--skills", "build/escrow_cya/skills",
             "--out", "out/escrow_cya"],
    "envFile": "${workspaceFolder}/.env",
    "justMyCode": true
  }]
}

No GPU is needed, because both models are called over HTTPS. A laptop is enough. --sync skips the Batch API so a first run finishes in minutes rather than waiting on a batch.

Open decisions

  • What shape the final verdict output takes, for example one key per check plus an overall result.
  • How manual review appears in the workflow: a NEEDS_HUMAN value, a route, or a gate.
  • Which model name generated LlmAgents should use at runtime.
  • Whether hand-written escrow_cya YAMLs exist to compare against.
  • Answers from the metadata owner on P309, LMT type, H87, G47, G81 and T32. Until then, checks that need them route to manual review.
  • How to read AMBC1 lines 419–420. The current reading is "check ICMP first, else additional research".
