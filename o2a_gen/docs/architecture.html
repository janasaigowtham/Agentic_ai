o2a_gen · design v3 · playbook-driven

From a procedure and a playbook to O2A workflow YAMLs

o2a_gen takes five inputs and writes one YAML per agent. The playbook says how to build the workflow, the procedure says what to check, the tools and metadata supply every real value, and the agent syntax gives each YAML its form. Every input is compiled the Corpus2Skill way, with Opus cards, Nemotron embeddings and skill trees. Opus then applies the playbook in six stages, and code checks each stage's answer before the next one starts. The code holds no knowledge of any procedure, tool or agent class.

Opus 5.5 Anthropic API · Batch for compile, cached prompts for the harness Nemotron DeepInfra · nvidia/Nemotron-3-Embed-8B code splits, links, checks, writes files

End to end

Without a playbook, o2a_gen still runs its older step-by-step generator. Existing workflow YAMLs are never an input. They are used only by compare, after generation.

Harness stages

0

Recipe

Opus · effort high

Turns the playbook into a checklist: every role with its class, the condition that adds it and its output-key pattern, plus the orchestration, logic, data and naming rules, and the requirements the finished workflow must meet.

Code checkeach role's class exists in the syntax
Savesworkflow_recipe.json
1

Logic

Opus · effort high

Applies the playbook's logic rules to the procedure. It finds the parts that define checks, such as the attribute instructions, and records each attribute's checks in order, with what each reads, its If/Then rules, its outcomes and any outside system it needs. Ambiguities are listed, not guessed.

Code checkattributes and checks exist; check ids are unique; every cited line exists
Savesworkflow_flow.json / .md
2

Data map

Opus · effort high

Applies the playbook's data rules. Every value a check reads becomes available (tool and field), derived (formula from named fields) or missing. Outside systems are mapped to the tools that serve them.

Code checkevery tool and field name marked available must appear in the tools or metadata; derived values need a derivation
Savesworkflow_data_map.json / .md
3

Orchestrate

Opus · effort high

Applies the playbook's roles and orchestration rules to the flow and data map. It decides every agent: name (from the tools where they name it), class, input and output keys, children, routes, the checks it covers, its sources and the playbook rule behind it.

Code checkclasses exist; names are unique; children and route targets exist; exactly one root; every key read is written by some agent or is an input; every check in the flow is covered
Savesworkflow_plan.json / .md
4

Write

Opus · effort medium · parallel

One writer per agent. Each gets its plan entry, the whole plan, the session keys available when it runs, its class syntax, the checks it covers, the data map, its procedure lines and the exact tool and metadata documents it names. Values are copied, and a missing value stays empty and is reported as a gap.

Code checkfields exist in the class syntax; every {{ }}, { } and :param refers to an available key; route targets are its children
Savesworkflow/*.yaml with a provenance header (playbook rule, checks, lines, sources, TODOs)
5

Review and fix

validatorOpus · fresh context · effort high

The validator checks the files: YAML, file names, key flow, routers and connections. A fresh Opus reviewer checks them against the recipe, the flow, the data map and the syntax. Each blocking finding and each validator error goes back to that agent's writer with the fix. This repeats for up to 2 rounds (generation.review_rounds).

Savesworkflow_review.json, workflow_placeholders.md, workflow_report.json
In the UIbuild notes buttons: flow, data map, plan, placeholders

Prompt caching

Every harness call starts with the same system prompt, so it is cached once and read at $0.20 per million tokens instead of $4. The task part differs for each call.

rulesnever invent a value
playbook (full)≈ size of your playbook
agent syntax (full)≈3.5k tok
TASK: recipe · logic · datamap · orchestrate · write · reviewstage inputs

Compile calls (cards, folder pages, section summaries) run through the Batch API at half price, with their own cached instructions.

Example: AMBC1, attribute Q25722

logic: checks 1–5.7, step 4 needs ICMP→data map: ANA1/LAST1 → ESCROW_LAST_ANALYSIS_DATE · H87 → missing→orchestrate: ICMP chain first, gate, data_fetcher, q01 checkpoints, verdict→write: URLs, auth and SQL copied from the tools file

The target shape for this run is the Q25722 Agent Flow. If a run differs, the build notes show which stage made the difference.

What embeddings do here

The harness stages read the inputs in full, so the workflow doesn't depend on search. Nemotron organises the skill trees, links each procedure section to its likely tools, data and playbook rules, and backs the navigator's search when a name doesn't match exactly. Fine-tuning the embedding model isn't needed. It would only matter if inputs grew too large to pass in full, and then you'd measure retrieval first.
