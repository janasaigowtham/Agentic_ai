o2a_gen Architecture

How a review procedure, plus the O2A agent syntax, data metadata and tools, becomes a validated set of O2A agent YAMLs. Both the procedure and the catalog are compiled into skill trees (Corpus2Skill's compile-then-navigate), then each step is turned into an agent. The page covers the system view, then every stage end to end with real samples. Uses the compile-then-navigate technique from Corpus2Skill. Every model call goes through Tachyon.

System view

LLM calls a Tachyon model EMB embedding model code no box badge: plain, deterministic code reads the compiled catalog read only after generation

End to end, step by step

This follows one example through every stage: the PMI deletion denial (DDN) review from the test fixtures. Each stage lists what it reads, what it does, what's checked, and what it hands to the next stage, with a real sample of that output. Loan data never appears: the procedure and catalog hold only reference material.

C1

Collect & split

catalog.pycode
Reads
catalog_src/: schema/ (required), metadata/, tools/, reference/. An agents/ folder is ignored with a warning.
Does
Turns every source into one document per thing:
  • Agent syntax: split on headings that name an agent_class, so ## database_agent becomes the document "database_agent". Other sections become "general" rules.
  • Metadata CSV: one document per table, from its rows.
  • SQL DDL: one document per CREATE TABLE.
  • Tools: one document per tool.
  • Reference files: split on headings if long.
Each document gets a short, stable ID: its kind letter plus a hash.
Checks
Stops if there is no agent syntax.
Output

C2

Document cards

skilltree.make_cardsLLM
Does
One call per document, using the catalog_cards model, returns a title, a one-line summary and up to 8 keywords (exact table, column, tool and field names).
Checks
The reply must be JSON with a title; otherwise it retries. If it still fails, it falls back to the document name.
Cache
cards.json stores a hash of each document's content. On a rebuild, only new or changed documents are sent to the model.
{"title": "MSP_LOAN_MASTER7_CS",
 "one_line": "Loan master table with investor class and ICMP letter date.",
 "keywords": ["MSP_LOAN_MASTER7_CS","LN_NO","INV_CLASS_CODE","LETTER_EFFECTIVE_DATE"]}
C3

Embed

skilltree.embed_textsEMB
Text
"{title}. {one_line} {keywords}\n{first 2000 chars}". The card goes first so documents group by subject, not by DDL formatting.
Model
local: sentence-transformers on this machine, in batches of 32; nothing leaves the machine. llm: Tachyon embed().
Output
One vector per document, scaled to length 1, so a dot product equals cosine similarity (1 means the same meaning, 0 means unrelated). Used in C4 to form folders, and saved (vectors.npy, with the model name) so that G1 can match procedure sections to the most similar tools and data. If the embedding model changes, the saved vectors are ignored and the catalog has to be rebuilt.
C4

Partition into folders

skilltree.split · kmeanscode
  1. By kind first: agent-syntax/, data-metadata/, tools/, reference-docs/. A table can never share a folder with a tool.
  2. Recursive split within each kind: if a group has more than leaf_max (12) documents, use k = clamp(⌈n/12⌉, 2, branching 8) and cluster.
  3. Cosine k-means:
    • Seed the starting points with k-means++, so they begin far apart.
    • Assign each document to the centre it's most similar to (argmax X·Cᵀ).
    • Move each centre to the average of its documents, rescaled to length 1.
    • Repeat until nothing moves, or 50 rounds.
  4. Fold small groups (fewer than min_group) into the most similar group, then recurse, up to max_depth 4.
  5. Fixed seed: the same documents and model always produce the same folders.

For example, 60 tables become 5 folders of about 12. 300 tables become 8 folders, each split again into about 3.

G0

Guards before anything runs

generate.pycode

It refuses to run if:

  • the catalog contains agent documents;
  • the catalog was built from files inside the --compare-with folder;
  • --compare-with is the output folder;
  • the output folder already has YAMLs (unless --overwrite).

Existing YAMLs are not opened until G7.

G1

Compile the procedure into a skill tree

proctree.pyLLM EMB

The procedure is the corpus in the Corpus2Skill sense. Its steps are what the pipeline must answer, and the catalog holds what the answers are built from. This stage gives it the same treatment as the catalog: split, summarised and embedded. One difference: its folders follow the procedure's own headings, in document order, because the order of steps is the workflow and topic clustering would scramble it.

Split
Headings form the tree: ## 1. Pre-process becomes folder procedure/02-1-pre-process/, and the number prefix keeps the order. Each section's own text becomes a document (p + hash) with its line range; long sections are split on blank lines. Text before the first heading becomes a "Preamble" section.
Summarise
One call per section, bottom-up, using the catalog_summary model. A parent's summary is built from its own text plus its sub-sections' summaries.
Embed
Each section document (title + summary + text), with the same embedding model as the catalog.
Link
  • Related sections: the 3 most similar other sections of the procedure. This is how a step finds definitions, appendices or rules stated elsewhere.
  • Likely tools & data: the 5 most similar catalog documents (metadata, tools, reference; agent syntax excluded), scored against the catalog's saved vectors.
Output
generated/pmi_ddn_procedure/: .claude/skills/procedure/…, documents.json, catalog_index.json, procedure_links.json. Set generation.compile_procedure: false to skip this stage.

G2

Extract steps from the procedure

procedure.pyLLM
Reads
The whole procedure, sent to the extract model with every line numbered so each step can cite its source, plus the section outline and summaries from G1. The whole text is read here so no step can be missed.
Does
Returns phases → steps, each with:
  • a kind: lookup, compute, review, decision or approval;
  • what it produces and which earlier steps it uses;
  • for decisions, the step it depends on and its branches.
Two rules: a complex condition gets its own compute step that produces a flag, and branches that produce the same outcome use the same wording.
Checks
Step IDs are unique; uses points only to earlier steps or inputs; each decision has at least two branches, none empty; every cited line number exists in the procedure. A failure is sent back with the error, for up to 3 tries.
Output
generated/pmi_ddn_steps.json

G3

Plan the agent tree

plan.pycode
Class
lookup → database_agent · compute → slv_transformation_agent · review → LlmAgent · decision → decision_router_agent · approval → agent_gate
Structure
  • The whole procedure becomes a resumable_orchestrator.
  • Each phase becomes a SequentialAgent, unless it's only a router or a gate.
  • A branch with several steps becomes a SequentialAgent.
Names & keys
  • Names are prefix_ + the step title, in snake_case; output keys are prefix_ + what the step produces. Both are de-duplicated.
  • uses becomes the required keys.
  • Each agent records the available keys at its point in the flow.
  • Mutually exclusive branches that produce the same thing share one key.

├─ pmi_ddn_icmp_decision_router        decision_router_agent

G4

Ground each agent

navigator.py · ground.pyLLM

Runs for every agent that came from a procedure step, several at once (--workers). Container agents (orchestrator, sequences) need no model call.

a · Browse the catalog navigate model, up to 12 turns

The step's cited line is mapped to its procedure section, and this context is given both to the navigator and to the writer:

This step is in procedure section `procedure/02-1-pre-process` (lines 7-10), doc `p419a06197ba3e`.
Related procedure sections (by similarity):
- `pa8a4cb0e4866b` 4. Post-process (0.52)  …
Likely tools & data for this section (by similarity; verify before use):
- `r303a0a389a5db` [reference] investor_guidelines (0.59)
- `m5520d20d37cd2` [metadata] MSP_LOAN_MASTER7_CS (0.53)  …

The navigator browses one combined tree: procedure/ plus the catalog folders. The model sees the step, its section context and the top-level folders, and replies with one JSON action per turn. The code runs the action and sends back the result. Reads can't leave the catalog folder. Routers skip this, since they only need the upstream flag.

→ {"action":"find","term":"MSP_LOAN_MASTER7_CS"}
← - doc `m5520d20d37cd2` [metadata] MSP_LOAN_MASTER7_CS
  - entity 'MSP_LOAN_MASTER7_CS' appears in: data-metadata/msp-loan-tables
→ {"action":"read","path":"data-metadata/msp-loan-tables/INDEX.md"}
← (folder listing, as in C5)
→ {"action":"get_document","doc_id":"m5520d20d37cd2"}
← [metadata] MSP_LOAN_MASTER7_CS  Table columns: LN_NO (CHAR(10)) … LETTER_EFFECTIVE_DATE (DATE) …
→ {"action":"done","doc_ids":["m5520d20d37cd2","m29b3bf74a3f2c"],
   "notes":"table + ECRM connection note"}

b · Write the fields ground model, 1 call + retries

The prompt is assembled from:

  • The agent syntax for this class, always included and placed first, followed by the general rules.
  • The agent's name and class, the procedure step and its source lines.
  • The output key, the available keys and the required keys; for routers, each branch → target agent.
  • The step's procedure section context: its section, related sections and likely tools & data (from G1).
  • The catalog documents chosen in (a), in full.
  • The JSON shape to return for this class.
{"db_type": "teradata", "connection_env": "ECRM_DB_CONN",
 "query": "SELECT M7.LN_NO, TRIM(M7.INV_CLASS_CODE) AS inv_class_code,
                  M7.LETTER_EFFECTIVE_DATE AS letter_effective_date
           FROM MSP_LOAN_MASTER7_CS M7
           WHERE M7.LN_NO = LPAD(TRIM(CAST(:loan_number AS VARCHAR(10))), 10, '0')",
 "params": ["loan_number"], "description": "Fetch MSP loan fields.", "gaps": ""}

c · Check, retry, derive

ClassRejected when
database_agentSQL binds a key that isn't available; a bound key is missing from params; the connection isn't an env var name
transformationtransform doesn't produce the output key, or uses {{ keys }} that aren't available
LlmAgentthe instruction is too short, uses {keys} that aren't available, or names tools that aren't in the catalog
routerthe routes aren't exactly one per branch; a key isn't available; an operator isn't allowed; a priority isn't an integer

A rejected answer goes back to the model with the exact error. In the tests, the verdict agent first references {pmi_ddn_borrower_ssn}, which doesn't exist. It is rejected with the list of available keys, and the second answer is used.

After acceptance, input_keys is derived from what the SQL, instruction or transform actually references, so an agent can never read a key it doesn't declare. A required key the agent doesn't read produces a warning. Fields the class syntax requires beyond these (e.g. a gate's resume_event) come back in extra.

G5

Emit YAMLs

emit.pycode

Writes one file per agent in O2A layout:

  • default_db_yaml as an embedded YAML string;
  • multi-line text as block text;
  • sub_agents for containers;
  • per-class agent_templates merged in.

Each file starts with a comment naming the procedure step and lines it came from.

# Review before use.

agent_class: database_agent
description: Fetch MSP loan fields.
input_keys:
- loan_number
output_key: pmi_ddn_msp_loan_data
default_db_yaml: |
  type: teradata
  connection:
    url: ${ENV:ECRM_DB_CONN}
  query: |-
    SELECT M7.LN_NO, TRIM(M7.INV_CLASS_CODE) AS inv_class_code, …
    WHERE M7.LN_NO = LPAD(TRIM(CAST(:loan_number AS VARCHAR(10))), 10, '0')
G6

Validate

validate.pycode

Reloads the written files and walks the pipeline in execution order, tracking which keys are written:

  • Sequences add each agent's key in turn.
  • Routers fork. After a router, a key written by every branch counts as present; a key written by only some branches is "maybe" and produces a warning when read.

It also checks:

  • missing agents, and file/name mismatches;
  • undeclared references in instructions, transforms and SQL;
  • literal connection URLs instead of ${ENV:VAR};
  • router targets vs sub_agents, duplicate priorities, a missing default route;
  • several agents writing one key (unless they are in exclusive branches);
  • fields that don't appear in the class's agent syntax.
WARN  router-default pmi_ddn_icmp_decision_router: no default route: if no condition matches, nothing runs
10 agents, 0 errors, 1 warnings.
G7

Compare with existing YAMLs (optional)

compare.pycode

Runs only with --compare-with, after G6. It matches each existing agent to a generated one:

  1. by the same name;
  2. otherwise by the same output_key and class;
  3. otherwise by a similar name (at least 0.6).

It then scores the matched pairs.

gold_agents                10       output_key_agreement       1.0
generated_agents           10       mean_input_keys_jaccard    0.9
matched                    10       db_table_agreement         1.0
coverage                   1.0      missed_gold_agents         []
class_agreement            1.0      extra_generated_agents     []

These figures come from the offline test run on the fake model, against a PMI DDN-style reference set. Input-key overlap is 0.9 because the generated router lists its flag in input_keys and the hand-built one doesn't. Real results depend on the Tachyon models and your catalog.

Tree shape, names and keys are fixed before any agent is written.

Ground prompt (per agent)

  • Agent-syntax section for its class, plus the general rules
  • Its procedure section, related sections, likely tools & data
  • The procedure step and its source lines
  • Output key, available keys, required keys
  • Catalog documents the navigator chose
  • A JSON schema for that class's fields

Report

  • coverage: step → agent
  • grounding: which catalog docs each agent used, the gaps the model reported, warnings
  • findings, errors, warnings
  • llm_usage: calls and tokens per model
  • comparison: only with --compare-with

What leaves your network

Sent to Tachyon

  • Compile: catalog document text (for cards) and folder contents (for summaries)
  • Generate: the procedure text (section summaries and step extraction); for each agent, its step and section context, the syntax section and the catalog excerpts it browsed
  • Embeddings: only if embedding.provider: llm

Stays local

  • Embeddings by default (provider: local, sentence-transformers)
  • Planning, YAML writing, validation, comparison
  • Existing agent YAMLs: read only by compare, after generation, and never sent to a model
  • No Skills API upload and no server-side code execution
  • Credentials: generated YAMLs reference ${ENV:VAR} only

Keep loan and borrower data out of catalog_src/ and the procedure. Only reference material belongs there.

Where it is checked

procedure.py
Step IDs are unique, uses points only to earlier steps or inputs, each decision has at least two branches, none empty, and every cited line exists. On failure, the model gets the error and retries (up to 3 tries).
ground.py
Per class: SQL :params are available keys and declared; the connection is an env var name; transform produces the output key; instruction {refs} exist; tools exist in the catalog; one route per branch with valid operators. Retries with the error. input_keys is derived from the actual references.
validate.py
Walks execution order: each key is written before it's read, with a warning when only some branches write it. Missing agents, file/name mismatch, literal credentials, router targets and default route, fields outside the agent syntax.
generate.py
Leakage guards: refuses a catalog that contains agent documents or was built from files in the comparison folder, and refuses a comparison folder that is also the output folder.
tests/o2a_gen
36 offline tests on a scripted fake model, run against both engines. They check that no text from the existing YAMLs appears in any model call and that each agent's prompt contains its class syntax.

Extension points

Change the model or provider

  • providers/tachyon_provider.py: three TODO blocks
  • models.* in config: extract, ground, navigate, catalog_summary, catalog_cards, llm_agent

Change what gets generated

  • plan.KIND_TO_CLASS: which agent_class each step kind becomes
  • generation.agent_templates: fixed fields per class
  • ground._SPECS: output schema and checks per class

Change the catalog

  • catalog.engine: native or corpus2skill
  • leaf_max, branching, max_depth, use_cards
  • embedding.provider and model
